# desktop 设计

## 职责与边界

**负责**

- 把「本机桌面窗口」变成可读、可查、可动、可复核的四件事：`screen` 截屏、`windows` / `uia` / `point` 读状态、`click` / `move` / `type` / `key` / `scroll` 发合成输入、`invoke --id` 走元素自带 UIA pattern 的语义操作。
- 把「动作到底有没有生效」变成可观测判据：每条注入命令自动取动作前后的状态并打印 `CHANGED=` + `BEFORE=` / `AFTER=`；坐标类命令另给 `GetCursorPos` 硬件回读的 `CURSOR_AFTER=` / `CURSOR_LANDED=`。
- 把「注入会不会被拦」在动作**之前**判定：目标完整性级别高于自身就阻断（`UIPI blocked: …`），不要事后靠"没变化"猜。

**不负责**（逐条防越权）

- 不做需求解读、不做方案设计、不决定"该不该点这个按钮" —— 那是调用方（拿到桌面工具链的子代理）的判断。
- 不绕过 UAC、不碰安全桌面（Winlogon / UAC 同意界面）、不做进程注入（`CreateRemoteThread` / `SetWindowsHookEx` / 反射 DLL）、不改系统设置（注册表 / 服务 / 策略 / 计划任务）、不驱动管理员权限进程。
- 不驱动网页 —— 网页交互是 `browser/` 的范围（它管 DOM 与 CDP，本模块看不见 DOM，只能看见浏览器窗口这一层）。
- 不做 OCR / 图像识别 / 视觉定位：本模块只出 PNG 与坐标读数，"图里是什么"交给调用方的多模态能力。
- 不注册任何 DSH 工具、不写插件 manifest：它是**路径**（`${DSH_HOME:-~/.dsh}/desktop/cli.mjs`），不是全局工具名。
- 不管理登录态、不存凭据、不代填任何账号密码。

## 核心数据模型

### ScreenBox（虚拟屏）

一张**虚拟屏**覆盖全部显示器：`{ originX, originY, width, height }`。主显示器原点可以是负值（副屏在主屏左侧时 `originX < 0`），所以任何"把物理坐标换算成归一化坐标"的地方都必须**先减原点**。

- **I1**：对外坐标一律是**真实物理像素**，进程启动即声明 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2 = -4)`。来源：非 DPI 感知进程拿到的坐标被系统虚拟化（本机实测 1707×1067 vs 真实 2560×1600，系数 1.5）；载体：[机检] `dpiScale` 单测 + [真机] `profile` 的 `DPI_AWARE=PER_MONITOR_AWARE_V2` 且 `SCREEN=2560x1600`。
- **I2**：归一化公式是 `round((x - originX) * 65535 / (width - 1))`，**分母是尺寸减一**。来源：`MOUSEEVENTF_ABSOLUTE` 的 0..65535 映射覆盖的是像素索引 `0..width-1`；载体：[机检] `toAbsolute` 单测（含负原点）；[真机] `click --dry-run` 印出的 `WILL_SEND_NORMALIZED` 与手算一致。

- **I2b**：**坐标类命令在注入前必须做一次几何自洽检查**（`Get-GeoCheck`）：把目标窗口的 `GetWindowRect` 与同一个顶层窗口的 UIA 根元素 `BoundingRectangle` 逐边比对（容差 2 px），再把"请求点上的 UIA 元素自身矩形"与该点比对，输出 `GEO_WINDOW_RECT=` / `GEO_UIA_ROOT_RECT=` / `GEO_POINT_RECT=` / `GEO_MISMATCH=true|false|unknown`。矛盾时**默认不发事件**：`GEO_MISMATCH=true` + `UsageError`（退出码 2），只有显式 `--force` 才硬发（并打 `WARN=`）；`unknown`（**这一路需要的读数有一条没取到** —— 判据缺测绝不许被读成"一致"：`false` 只在两套读数都取到且都印证时才给。唯一的例外是 `uia --hwnd` 这一路本来就没有查询点，它走 `geoVerdict` 的 `requirePoint: false`、只验根矩形一致，并在 `reasons` 里写明"这一路没有查询点"）另打一条 `WARN=` 说明不能当成"几何一致"。来源：真机踩过 —— 靶窗口最大化时 `windows` 报 `-11,-11,2582,1550` 而 `uia --hwnd` 给的是与客户区布局吻合的另一组矩形，照 `uia` 那组算出的 `--x/--y` 在 `point` 里解析成**另一个控件**，`CHANGED=false` 而人以为点对了；窗口复位后两套读数和睦。载体：[机检] `geoVerdict` / `rectsAgree` / `rectContains` 单测（三态 + 容差）；[真机] `point` 与 `click --dry-run` 的 `GEO_*` 四行。
- **未观测**：`GEO_MISMATCH=true` 在真机最大化窗口上是否真能抓到那次坐标错位 —— 本机受限会话里 `FromPoint` 被拒（`GEO_POINT_RECT=` 为空），只验到 `GEO_WINDOW_RECT` 与 `GEO_UIA_ROOT_RECT` **一致**（`-11,-11,2582,1550` 对 `-11,-11,2582,1550`，`GEO_MISMATCH=false`）。量法：完全权限会话里把靶窗口最大化，跑 `node cli.mjs point --x <靶内一点>`，看是否出现 `GEO_MISMATCH=true` 与那条 `WARN=`；再跑不带 `--force` 的坐标类命令，期望**在注入前**就以退出码 2 停下。
- **I3**：`SendInput` 的绝对移动标志**必须同时含** `MOUSEEVENTF_ABSOLUTE (0x8000)`、`MOUSEEVENTF_VIRTUALDESK (0x4000)`、`MOUSEEVENTF_MOVE (0x0001)`。来源：本机实测 —— 只给前两个时 `SendInput` 返回 `rc=1 err=0` 而**光标纹丝不动**；`VIRTUALDESK` 在单屏且虚拟原点 `0,0` 时与不带有**相同的实测落点**（本机单屏实测无差异），但多屏/负原点下缺它会把坐标解释成主屏内的相对量 —— 所以它是**正确性要求**，不是"本机可观测差异"。载体：`bridge.ps1` 四处 `New-MouseInput -Flags 0xC001`（`0x8000|0x4000|0x0001`）+ [机检] `test/injection.test.mjs` 断言编码后的 `dwFlags == 0xc001` + [真机] `move --x … --y …` 后 `CURSOR_LANDED=true`。
- **未观测**：多显示器布局（负原点、各屏不同 DPI）从未在本机实测过 —— 本机只有一块屏（`MONITORS=1`、虚拟屏原点 `0,0`），负原点只有单测的假数据覆盖。量法：接上第二块屏（或把主屏换成右侧），跑 `node cli.mjs profile` 看 `VIRTUAL_ORIGIN` / `VIRTUAL_SIZE` / `MONITORS` 是否随之变化，再 `node cli.mjs point --x <副屏上一点的物理坐标>` 看 `HWND` 与 `screen` 的 `ORIGIN` 是否自洽。

### WindowRecord（顶层窗口）

`{ hwnd, rootHwnd, pid, process, class, title, rect:{left,top,width,height}, integrity }`。

- **I4**：`WindowFromPoint` 返回的是**最深的子窗口**，对外必须先用 `GetAncestor(hwnd, GA_ROOT = 2)` 归一成顶层窗口再取 pid / class / title。来源：本机实测 —— 直接取会命中 `Chrome_RenderWidgetHostHWND` 这类无标题子窗口；载体：[真机] `point` 输出的 `ROOT_HWND` 与 `windows` 列表里那一行一致。
- **I5**：`integrity` 读不到就写 `unknown`（诊断信息写进 `unknown(rid=N)`），**不许默认成比自身低**。来源：受限令牌下 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` 对某些进程返回 `ERROR_ACCESS_DENIED`；载体：[真机] **读数随调用方的令牌而变** —— 早期受限会话下 brave (PID 1816) 那三行是 `unknown`（不是报错），返工复测时同机同进程读回 `medium`。所以 `unknown` 表示的是"**这次调用**读不到"，不是"这个进程读不到"；判据是那一行既不是空也不是编造的值，且 `decideInjection` 对 `unknown` 一律按 `block-integrity-unknown` 处理（fail-closed）。
- 进程名的主路径是 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION = 0x1000)` + `QueryFullProcessImageNameW`，`Get-Process` 只作兜底。来源：受限令牌下 `Get-Process` 对任何 PID 都取不到 `ProcessName`；且 `QueryFullProcessImageNameW` 的 `StringBuilder` 重载会**静默只回第一个字符**（进程名显示成 `C`），必须用 `byte[]` 缓冲 + `Encoding.Unicode.GetString(buffer, 0, size*2)`。载体：[真机] `windows` 的进程名是 `brave` / `QQ` / `explorer` / `WindowsTerminal`。

### ElementSnapshot（UIA 元素）

`{ id, runtimeId, controlType, name, automationId, rect, patterns[] }`。

- **I6**：元素的稳定 id 是 `el_<fnv1a32(runtimeId 的连接串) 的 8 位十六进制>`，**跨进程、跨快照稳定**。读法只有一条：**id 不同 ⇒ 元素必不同**（id 是 runtimeId 连接串的哈希）；**id 相同 ⇒ 不保证是同一个元素** —— `GetRuntimeId()` 读不到的元素全被折叠成同一个 id（`el_unknown`，见 I6e），而同一份快照里也可能有两个元素共享一个 id（两个元素报了同样的 runtimeId 连接串）。这层分工要读清，别留给读者推理：**I6 承诺的是"id 值本身确定"** —— 同一个元素在它的生存期内、跨进程跨快照算出来的 id 都一样；**它不承诺"拿这个 id 去动手一定只命中它"**（可命中性归 I6d 管：id 只在取它的那次遍历里稳定），也**不承诺"两次遍历里的同名命中是同一个元素"**（那由 I6f 的身份复核管）。来源：UIA runtime id 由 provider 分配、在同一 UI 元素的生存期内不变；载体：[机检] `elementId` / `fnv1a32` 单测（固定参考值：`''`→`811c9dc5`、`'a'`→`e40c292c`、`'42.1000.7'`→`5050afed`、`'42.65552'`→`ef243646`、`'保存'`→`a9629697`、`'DeepSeek Harness'`→`1478b7ff`）；[真机] 一个进程里 `uia --depth 2 --limit 5` 得到 `el_ef243646`，**另一个新进程**里 `uia --id el_ef243646` 报 `FOUND=true`。
- `pickElement(elements, {id, name})` 是"不许猜"的护栏：没给选择器 / 给的名字命中 0 个或命中多个 / id 不在快照里 ⇒ 返回 `reason`，不返回一个"最像的"元素。
- **I6b**：元素的 `patterns` **必须是字符串数组**（空数组表示"真的没有可用 pattern"）。桥侧只允许**一处**包装：`Get-PatternNames` 用 `return ,@($names)` 保住"单元素也当数组"，调用点用 `[object[]](Get-PatternNames …)`（**不许再加 `@()`**）。来源：两层包装叠起来会得到 `{"patterns":[["InvokePattern"]]}`，而 `patternList()` 会把它归一化成空列表 —— 与"这个元素不支持语义操作"**完全同形**，于是 `invoke --id` 对**每一个**元素都报"没有任何可用的语义 pattern（可用：-）"，输出里一处报错都没有。另有第二个坑：`return @($names)`（去掉逗号）在空数组时让 `ConvertTo-Json` 写出 `{"patterns":null}`。因为坏形状会被兜底函数吞掉，另设独立检查 `patternShapeProblem(patterns)`（裸字符串 / 内嵌数组 / 非字符串项各给一句话），`uia` / `point` / `invoke` 三条路径都打 `WARN=patterns 形状异常：…`。载体：[机检] `test/patterns-shape.test.mjs`（原始 JSON 里不许出现字面 `"patterns":[[`；同一元素在 `uia --depth` 与 `uia --id` 两条路径下 `deepEqual`；文本行第 4 列与 JSON 逐行一致）+ `patternShapeProblem` 单测；[真机] `uia --depth` 里 `Window` 元素的 patterns 列显示 `WindowPattern` 而不是 `-`。
- **I6c**：`uia --id <el_id>` **不裁剪** `elements` —— 它走的是同一份快照，命中信息落在 `found` 与该 id 在 `elements` 里的那一项；下游 `invoke` 就是拿这份快照 + `pickElement(elements, {id})` 定位的（`--id` 与 `--name` 两条查询路径必须给出逐值相同的信息）。载体：[机检] `test/patterns-shape.test.mjs` 的 `deepEqual` 与"同一 el_id 在快照里唯一"断言。
- `chooseAction(element, {setValue})` 按 `Invoke → Toggle → SelectionItem → ExpandCollapse` 的固定优先级选语义动作；给了 `--set-value` 就必须有 `ValuePattern`，否则返回 `{error}`。**只有容器类 pattern（如 `WindowPattern`）时同样返回 `{error}`**（"可用：WindowPattern；它可能只是个容器"）—— 有 pattern 不等于有**可执行的**动作，这一格不许猜。
- **未观测**：**本机受限会话里一条 UIA pattern 都没观测到** —— 全屏 `uia --depth 8`（上限 900，实收 53 个元素）里每个元素的 `patterns` 都是空的，`InvokePattern` / `ValuePattern` / `TogglePattern` / `SelectionItemPattern` / `ExpandCollapsePattern` / `TextPattern` 计数**全为 0**；另写了一个**同进程**探针（WinForms `Form` + `Button`，`FromHandle` 取 `AutomationElement`）在同一进程里也取不到 `InvokePattern`，且那个按钮被报成 `ControlType=Pane` 而不是 `Button`。⇒ 高度怀疑是本会话 Low 完整性级别下跨完整性 UIA provider 受限，**不是选择器写错**。量法：在完全权限（`danger-full-access`）会话里跑 `node "${DSH_HOME:-~/.dsh}/desktop/cli.mjs" uia --depth 6`，看 `InvokePattern` / `ValuePattern` 是否出现。已由另一路完全权限会话实测到：自建按钮窗口 `Invoke()` ×2 与 `SetValue()` ×1 都真的改变了 UI 且光标未移动；同时也有覆盖面边界 —— Notepad3 的 5 个子元素全是 `ControlType=Pane` 且**无任何 pattern**（该应用没实现 UIA provider），File Explorer（`CabinetWClass`）能枚举 172 个后代但有元素 `SetValue` 被拒、异常原文是 `值为只读。`。

- **I6d**：**元素 id 与快照作用域绑定。** `el_…` 是 UIA runtime id 的哈希，只在**取它的那次遍历**里稳定；桌面一拥挤，从桌面根做的遍历会在 `--limit`（**遍历预算**，默认 3000）处停下并报 `TRUNCATED=true` / `SNAPSHOT_TRUNCATED=true`。所以「这次快照里没有 X」**不等于**「X 不存在」—— 三种原因（元素消失 / 换了作用域 / 快照被截断）必须都能被说出来，不许在 `pickElement` 的 `reason` 里下结论。真机实测：`uia --depth 20 --json` 得到 `count=3000 truncated=true` 且**不含**目标窗口，而同一秒 `uia --hwnd 0x630594 --depth 6` 只有 3 个元素、目标就在里面 —— 于是"在根快照取 id、紧接着 `invoke --id`"11/11 全失败，报的却是"元素可能已消失"。`invoke` 因此有 `--hwnd` / `--name` / `--depth` / `--limit` 四个作用域选项，并把 `SNAPSHOT_SCOPE=` / `SNAPSHOT_COUNT=` / `SNAPSHOT_BUDGET=` / `SNAPSHOT_TRUNCATED=` 全打出来；截断状态下找不到 id 时**报的是截断**，并叫人加 `--hwnd` 后用**同一作用域**重新取 id。载体：[机检] `test/plan.test.mjs`（`invoke --id el_00000000 --limit 3` ⇒ 退出码 2、stderr 含「快照被截断」与「≠「这个元素不存在」」、且**不含**「元素可能已消失」；`snapshotScopeText` 单测）。

- **I6e**：**`el_unknown` 是"`GetRuntimeId()` 读不到"这一类元素的折叠 id，不是"某个元素的名字"，也不能当身份用。** 写出它的地方只有桥的节点构造：`GetRuntimeId()` 抛了就把 `id` 写成 `el_unknown`、`runtimeId` 写成空串（正常生成的 id 仍是 `el_<fnv1a32(连接串)>`）。所以**形状闸门不变**（`isElementId('el_unknown') === true`），它**必须继续出现在 `uia` / `point` 的快照输出里** —— 那是唯一的诊断面，藏起来就等于说"这个元素不存在"，触犯 I6d 的同一条禁令。但"能看见"不等于"能动手"：一份快照里**恰好一个** `el_unknown` 就能过 `pickElement` 的命中数闸门，而桥的第二遍遍历取的是**第一个** `el_unknown` —— 这不需要任何竞态，也不必是同一个元素；不给 `--hwnd` 时两者甚至可能不在同一个窗口。所以 `invoke --id el_unknown` **必须**显式给 `--hwnd`，否则 `UsageError` + 退出码 **2**，错误文本要说清"占位、不唯一、必须限定窗口"（**不是**"元素不存在"）。限定窗口后它仍然没有身份可复核 ⇒ 走 I6f 的 `absent` 一路（`ID_IDENTITY=absent` + 一条 `WARN=`）。载体：[机检] `test/pure.test.mjs`（`PLACEHOLDER_ELEMENT_ID` / `isPlaceholderElementId`）、`test/cli-contract.test.mjs`（`invoke --id el_unknown` ⇒ 2，stderr 含「不唯一」「--hwnd」「限定窗口」）。
- **I6f**：**元素身份随 `invoke` 一起下发；对不上就一步都不动。** 桥新增**可选**参数 `ElRuntimeId`（与 `ElId` 并列，缺省空串 ⇒ **老调用方式行为完全不变**）。`Do-InvokeChosen` 在**动手路径上的任何动作原语之前**（`.SetValue(` / `.Invoke()` / `.Toggle()` / `.Select()` / `.Expand()` / `.Collapse()`）先比一次身份：`Get-ElementIdentityGate -Expected $ElRuntimeId -Actual ([string]$node['runtimeId']) -ElementId $MatchId`（**规则本身不在这行字面量里** —— 唯一实现是 `scripts/identity.ps1` 的 `$Actual -eq $Expected`，见下），不一致就写 `invoked=false` / `identityMismatch=true` / `patternError='element identity mismatch: id matched but runtimeId differs'` 并**立刻返回** —— 一个 pattern 都没取、一个动作都没执行。**口径（别读成更强的话）**："动手路径的任何动作原语之前"**不是**"文件里第一个 `TryGetCurrentPattern` 之前" —— 构建节点记录时（本文件里，以及构建快照时）`Get-PatternNames` 就已经对每个节点 `TryGetCurrentPattern` 过一次，那只是**只读枚举**（清点这个元素有哪些 pattern），不是动作；不许发生的事是"身份不吻合之后还为了动手去碰这个元素"。判定本身**不写在这里**：唯一实现在 `scripts/identity.ps1`（`Get-ElementIdentityGate`），`bridge.ps1` 与 `test/fixtures/invoke-identity-bridge.ps1` 都 dot-source **同一份** —— 否则一份只读源码的守卫只能发现"字面量没了"，把判定条件改成永假也照样全绿（这是对抗性验收实测出来的缺口）。CLI 侧把**定位快照**里 `picked.element.runtimeId` 原样下发；快照没给这个字段时**不下发**（不许凭空造一个），并打 `ELEMENT_RUNTIME_ID=`（空）+ `WARN=这次没有身份复核…`，让缺口在输出里看得见。`ID_IDENTITY=` 是三态：`checked`（下发了身份且一致）/ `absent`（这次没有身份可复核）/ `mismatch`（不一致）。**`mismatch` ⇒ 拒绝动手、退出码 2**，与"动作没生效"的 **1** 分开：前者的补救是重新取 id（元素可能已被替换），后者是去查闸门与靶侧。为什么不改 id 形状、不掺世代号/祖先链指纹：I6 承诺"同一个元素在它的生存期内 id 不变"，掺进快照序号或祖先链指纹会**当场推翻**这条承诺；而缺口是"身份没随调用下发"，不是"id 不够独特"。载体：[机检] `test/element-identity.test.mjs`（假桥两次遍历报不同 runtimeId ⇒ 退出码 2 且 `OK=false`；一致 ⇒ 0；快照无 runtimeId ⇒ 0 + `absent`；静态守卫钉住闸门是**同源模块 `scripts/identity.ps1` 的调用点**、且在动手路径的任何动作原语之前（口径不是「文件里第一个 `TryGetCurrentPattern` 之前」：那只是只读枚举，写成那样会恒真））、`test/params-map.test.mjs`。

- **已知缺口（登记，未修）—— `--fallback-point` 的坐标回退不经过身份复核（F4）**：I6f 的身份复核只在这条路上生效：`invoke` 走元素自带的 UIA pattern。调用方显式加了 `--fallback-point` 而元素没有任何可用 pattern 时，`cmdInvoke` 用**定位快照**那块 `rect` 的中点退化成一次坐标点击（`cli.mjs` 的 `cmdInject(<synthetic>, 'click')`，见红线 4），下发的 `params` 里既没有 `ElId` 也没有 `ElRuntimeId` ⇒ **这条路上"两次遍历命中的是不是同一个元素"无从谈起**：`el_unknown`（即使已按 I6e 限定 `--hwnd`）与任何无 pattern 的元素都可以借坐标点一下，而落点判据（红线 15 / I7g）只回答"落点像素上的窗口是不是目标窗口"，不回答"点中的是不是那个元素"。**当前这样是刻意的**：这条退化的语义就是调用方**显式 opt-in** 的"这不是语义操作"，它会打 `WARN=`；I6f 要堵的是"以为自己在下发语义动作、实际动到了别的元素"，而这条路上调用方已经被告知不是语义操作。**要动它得先有落点判据** —— 把"落点像素上那个元素的身份"读出来与定位快照比一次（`point` 已能给出 `ELEMENT_ID`，缺的是与 `runtimeId` 的比对），属判据层立项，本次不做。载体：[机检] 无（缺口，未加守卫）；量法见 `testing-guide.md` 的同名未观测项。

### InjectionPlan（注入计划）

`{ kind, point, normalized:{dx,dy}, button, clicks, double, text, keys, wheel:{dwData}, raise, moveOnly }`。
`kind` 取值 `mouse` / `text` / `key`；`button` 为空串且 `clicks = 0` 表示**只移指针**（`move`，见 I7c）。

`decideInjection({ dryRun, force, ours, target })` 返回 `{ action, code, reason }`，`code` 取值 `can-inject` / `skip-dry-run` / `block-uipi-higher` / `block-integrity-unknown` / `forced`。

- **I7**：**成功判据是可观测差异，不是调用返回。** UIPI 拦下合成输入时 `SendInput` 会照常返回"已插入 N 个事件"且 `GetLastError=0`，事件随后被静默丢弃（本机实测：受限令牌 Low 完整性级别下 `rc=1 err=0` 而指针完全没动）。所以每条注入命令都在动作前后各取一次状态、打印 `CHANGED=true|false` + `BEFORE=` / `AFTER=`，坐标类命令另有一次 `GetCursorPos` 硬件回读（`CURSOR_AFTER=` / `CURSOR_LANDED=`）；`INSERTED_EVENTS=` / `LAST_ERROR=` 只作诊断，**不作判据**。载体：[真机] 完全权限与受限两种会话各跑一次 `click`，前者 `CHANGED=true`/`CURSOR_LANDED=true`，后者 `CHANGED=false`。
- **I7b**：`CHANGED` 是**三态** `true` / `false` / `unknown`，`VERDICT=` 分别写 `changed` / `no-observable-change` / `unknown`。口径是「**"我看不见这类动作的效果"绝不许报成 `false`**」：没有差异、且这次动作的效果落在已捕获判据的覆盖范围之外（既没抓像素、也读不到任何 UIA 内容属性）⇒ 报 `unknown` + `WARN=` 说明该怎么办（用 `--expect` 或自己读回）。来源：真机实测 `type` / `key` / `scroll` 全部报过 `CHANGED=false`，而靶窗口自己的 `TextChanged` 日志、独立 UIA `ValuePattern` 读回、滚动条 UIA 读数三者一致证明动作已生效 —— 真成功长得跟失败一模一样，会把人直接引向错误结论；反过来 `--double` 报过 `CHANGED=true` 而靶侧只数到一次点击。因此判据新增**内容类**一路（见 VerifyState）：焦点元素与 `--x/--y` 下落点元素的 `Value` / 文本选区 / `ScrollPattern` 百分比 / `RangeValue` / `Toggle` / `IsSelected`，逐条独立 try/catch，读得到的条数由 `CONTENT_BEARING_COUNT=` 报出。载体：[机检] `changeVerdict` 单测（可注入假状态，三种情形各一条）；[真机] 完全权限会话里 `type` / `scroll` 的 `CHANGED`。
- **I7c**：`move` **只移指针、绝不点击**。桥侧有 `-MoveOnly` 开关；不给它时鼠标分支因为 `$Button` 默认 `left` 会照样 append 一对 down/up —— 也就是说「移动指针」会变成一次点击，而 JS 侧手写的 dry-run plan 说只有 1 个事件，把这件事盖住了。来源：把 plan 改成由桥的**同一条构造路径**算（`-PlanOnly`，见 I7d）之后立刻暴露 —— `move --dry-run` 从自报 1 个事件变成桥报 3 个。载体：[机检] `test/plan.test.mjs` 的 move 用例（`EXPECTED_EVENTS=1`、`BUTTON=` 空、`CLICKS=0`）。
- **I7d**：**dry-run 的 plan 与实际注入必须同源。** `--dry-run` 不再由 JS 重算事件数，而是让桥用 `-PlanOnly` 走**同一条构造路径**（`$plan` + `expected = $inputs.Count`），只构造、不发送（不调 `SendInput`、不 `SetForegroundWindow`、不 `Raise-Window`、不 `AttachThreadInput`），输出 `PLAN_ONLY=true` / `PLAN_KIND=` / `EXPECTED_EVENTS=`。真跑时另打 `EVENTS_MATCH_PLAN=`（`INSERTED_EVENTS` 与 `EXPECTED_EVENTS` 是否相等；算不出给 `unknown`），不等时给 `WARN=`。来源：`click --double --force` 真机报 `INSERTED_EVENTS=3 CLICKS=1` 而 dry-run 自报 `CLICKS=2 EXPECTED_EVENTS=5` —— plan 与实际各算各的，于是"计划"成了假证据。载体：[机检] `test/plan.test.mjs`（7 条注入命令各钉一个期望值；dry-run 不许出现 `INSERTED_EVENTS` / `EVENTS_MATCH_PLAN`）；[真机] 见 `testing-guide.md` 的未观测项。
- **I7e**：**内容读数只许读属性，不许调 UIA 的文本/几何方法；整条内容探针还必须在独立子进程里跑。** 这条是被一次真机崩溃逼出来的：`TextPattern.GetSelection()[0].GetText(-1)` 会抛 `System.AccessViolationException`（`MS.Internal.Automation.UiaCoreApi.RawTextRange_GetText` → `TextPatternRange.GetText(Int32)`），而 AV 是 corrupted-state 异常 —— **PowerShell 的 `try{}catch{}` 抓不住**，参数求值时就炸掉整个进程，Node 侧只看到 `ERROR=bridge 没写出结果文件（exit=3221225477）`（`3221225477 = 0xC0000005 = STATUS_ACCESS_VIOLATION`）。触发面比想象大得多：**任何暴露 `TextPattern` 的 WinForms 文本框都会崩，空的（`len=0`）也照样崩**；同一个元素上 `DocumentRange.GetText(-1)` 反而正常返回（真机 `DOC_OK len=409`，全桌面 1130 个 `TextPattern` 元素逐个 `DocumentRange.GetText(200)` 全部跑完）——所以"换成正的 `maxLength`"不成立，差别在 selection 这条路径本身。15 行最小复现（另起进程即现）：建一个 `TextBox` + `Select(0,5)` → 取 `TextPattern` → `$tp.GetSelection()[0].GetText(-1)`。因此：①`Read-ElementContent` 里 `selection` 那条读数**整个删掉**（`ValuePattern` 的 `value` 已经覆盖"盒子里的内容变了"），函数里只许 `TryGetCurrentPattern` 取 pattern + 读 `Current.*` **属性**，源码里有 ASCII 的 POLICY 注释锁住这条；②内容探针从 `verify` 里挪出去，单列 `snapshot` 子命令，Node 侧用**容错通道** `probeBridge` 调它（崩溃 / 超时 / 无输出都映射成 `{ok:false, exitCode, crashed, crash, reason}`，绝不抛），所以一次崩溃只损失"这一次内容读数"、不会把整条注入命令带走；③缺测如实降级：`applyContentSnapshot` 把 `contentProbeFailed=true` 写进状态，`changeVerdict` 见到它就报 `CHANGED=unknown`（**像素哈希在也照样降级** —— 像素本来就看不见"文本框里的字变了"），`CONTENT_PROBE=failed` 打在输出里；调用方主动给 `--no-content` 时探针根本没跑，这一格写 `CONTENT_PROBE=skipped` 并另打一条 `WARN=` 说明这次的 `CHANGED=false` 只覆盖像素/窗口/前台/落点（写成 `ok` 会暗示内容类判据这次有效）；④`compareStates` 在任一端的 `contentProbeFailed` 为真时把内容这一类**整个退出差异集合**，否则"后一次没读到"（hash 变空串）与"界面真的变了"长得一模一样，崩一次就报 `CHANGED=true`（这条是写测试时才发现的，见载体）。载体：[机检] `test/content-safety.test.mjs`（剥掉注释行后 `bridge.ps1` 不许出现 `GetText(` / `GetSelection(` / `GetBoundingRectangles(` / `DocumentRange`；`VerifyCommand` 不许含 `Get-ContentSnapshot`、`SnapshotCommand` 必须含且不许含 `Send-Inputs`/`SetForegroundWindow`）；[真机] 完全权限会话里六条命令跑到"注入 + 打印结论"（本机受限会话只能验到 `snapshot` 自身不崩）。
- **I7f**：**判据按命令分工，读不到对应那一类就必须报 `unknown`。** `INJECTION_CRITERIA` 把"这条命令的效果要靠哪几类内容读数才看得见"写死：`scroll` → `scroll`（滚动位置）；`type` → `value`；`key` → `value` / `selected` / `toggle` / `scroll` / `rangeValue`。`changeVerdict(cmp, { needsKinds })` 在**两端的该类读数都为 0** 时报 `CHANGED=unknown` + `WARN=`（"这条命令的效果要靠「…」这类读数才能看见，而这次一条都没读到"），**不许报 `false`** —— 只有"读数读到了、而且没变"才轮得到 `false`。同时 `CONTENT_BEARING_COUNT=` 旁边加 `CONTENT_KINDS=` 逐类报数（例 `value=1,scroll=2,ancestorScroll=1`），因为总数会误导：`scroll` 要的是 `scroll` 那一类，读到 3 条 `Value` 什么也证明不了。`injectionWarn` 的引导句也按命令分开写（`scroll` / `type` / `key` / `move` 各一套），不再让 `scroll` 显示"可能是坐标落空"这类误导句。来源：真机 `scroll --x 521 --y 325 --dy -5` 报 `CHANGED=false VERDICT=no-observable-change`，而外部独立读数 `GetScrollInfo(SB_VERT)` 证明真的滚了（`nMin=0 nMax=79 nPage=5`，`nPos 0→15→30`；`dy=+5` 时 `26→22`）—— 内容探针只比文本属性，而滚动不改文本，所以这条命令的 `false` **结构上恒为假阴性**。另因为 `scroll` 移动的是**容器**的滚动位置、而光标下往往是容器里的 item（`ScrollItem` 而非 `ScrollPattern`），快照还会沿 `ControlViewWalker` 往父元素方向走 3 层（角色名 `ancestor1/2/3`，这一类另计入 `ancestorScroll`）；祖先链只对**一个**元素走（有 `--x/--y` 就用落点元素，否则用焦点元素），否则三处元素各走一遍会三倍化跨进程调用并产生重复行。载体：[机检] `test/pure.test.mjs` 的 `neededKinds` / `contentKindCount` / `changeVerdict` 单测（有 `scroll` 读数且没变 ⇒ `false`；没有该读数 ⇒ `unknown`，**像素哈希在也一样**）；[真机] 见下面的未观测项。

- **I7j**：**组合键里的单字符必须走 virtual key 路径，绝不许用 `KEYEVENTF_UNICODE` 直送。** `KEYEVENTF_UNICODE`（`flags=4`）注入的是**字符**，它绕过修饰键状态：真机 `key --keys ctrl+a --hwnd <靶>` 的靶侧结果只是插入了一个 `a`（`TEXTCHANGED len=2639→2640`，随后 `type --text V` 得到 `len=2641` —— 是**追加**，说明"全选"从未发生），而 CLI 那一侧一切正常（`EXPECTED_EVENTS=4 INSERTED_EVENTS=4 EVENTS_MATCH_PLAN=true`）。现在的规矩：`Parse-KeySpec` 先算出**一次**`$hasModifier`（"这一组里有没有修饰键"，唯一真相源），含修饰键的组里每个单字符都经 `Get-CharVirtualKey` 换成 `VK_*`（a-z 用"码 - 32"，标点走 `VkKeyScan` 随当前键盘布局，取不到就 `Fail`）、`path='char-as-vk'`、`flags=0`；**无修饰键的单字符**（`key a`、`type` 的文本）保留 Unicode 直送（`path='unicode'`、`wVk=0`、`wScan=<字符>`、`flags=4`）—— 那条路的目标是"在任何键盘布局下产出这个字符"，没有修饰键状态要照顾。`key A` 保留原样大小写（修前被小写化成 `a`）：单独用走 Unicode 直送（`SCAN=65`），配 `shift` 时走虚拟键、大写由**按住的 shift** 产生（不是把 `a` 换成 `A`，否则 `Shift+A` 与 `Ctrl+Shift+A` 会语义分叉）。未知键名 `Fail`（退出码 **1**、`unknown key name: …`），**不是**静默变成一个 `wScan=0` 的空事件。载体：[机检] `test/key-chord.test.mjs`（7 组组合键逐键断言没有 `FLAGS=4`、载荷 `vk` 是大写码 + 4 条静态守卫钉住 `$hasModifier` 是单一真相源、老形状不许回来）。**未观测**：`ctrl+a` 是否真的变成全选、`ctrl+c` / `shift+a` 是否落地；量法＝完全权限会话里对靶文本框跑 `key --keys ctrl+a --hwnd <靶>` 后跟一句 `type --text V`，期望靶侧是**替换**（`len` 变成 1）而不是追加。**这一步只修了"每一键长什么样"；真机复验随后证明光有描述符不够** —— 修饰键仍被"点一下"就松开，见 I7l。

- **I7l**：**组合键的发射顺序：修饰键全部按下 → 载荷键 down/up → 修饰键反向抬起。** 顺序由 `ConvertTo-KeySequence` 一次算好，每个事件带 `phase`（`modifier-down` / `key-down` / `key-up` / `modifier-up`），注入循环按 `phase` 决定是否 `-Up`（`$isUp = ($event.phase -eq 'key-up' -or $event.phase -eq 'modifier-up')`），`--dry-run` 的 `PLAN_KEY` 行把 `PHASE=` 打出来。来源：I7j 的描述符修好之后真机**仍然不通过** —— 旧分支是"每个描述符各发一对 down+up"，`ctrl+a` 实际成了 `ctrl↓ ctrl↑ a↓ a↑`（修饰键被点一下、主键单独按下）。三份独立的靶侧证据（WinForms 靶 `DSH-RV8`）：`ctrl+a` ⇒ `text=[HELLO]` → `[HELLOa]`（只插一个小写 `a`）→ 随后 `type --text V` ⇒ `[HELLOaV]`（**追加**，全选从未发生）；`ctrl+c` ⇒ `[HELLOaVc]`（要求零新增）；`shift+a` ⇒ `[HELLOaVca]`（**小写**，而大写正是"shift 真被按住"的判别量）。这三条在 CLI 侧全都显示 `EXPECTED_EVENTS=4 INSERTED_EVENTS=4 EVENTS_MATCH_PLAN=true FOCUS_SOURCE=hwnd` —— **事件数完全看不出顺序**，所以判据只能是 `PHASE=` 列，不能是数量。释放取**逆序**（后按先松）。**无修饰键时退化为原来的逐键 down/up**（`key a`、命名键、`type` 文本的行为不变：单个描述符仍是 2 个事件）。载体：[机检] `test/key-chord.test.mjs`（`ctrl+a` / `ctrl+shift+a` / `shift+a` 的 `PHASE` 序列、修饰键按下顺序与抬起逆序、`EXPECTED_EVENTS == plan.length`；静态守卫钉住 `ConvertTo-KeySequence` 存在、"注入按 phase 决定 Up"、老形状不许回来）。**未观测**：顺序修好之后 `ctrl+a` / `ctrl+c` / `shift+a` 在真机上是否真的成立；量法＝完全权限会话对靶文本框跑 `key --keys ctrl+a --hwnd <靶>` 后跟 `type --text V`（期望靶侧是**替换**、`len` 变 1，而不是追加）、`key --keys ctrl+c --hwnd <靶>`（期望靶侧零新增 `TEXTCHANGED`）、`key --keys shift+a --hwnd <靶>`（期望落地字符是大写 `A`）。
- **I8**：目标完整性级别**高于**自身 ⇒ 注入前阻断（`block-uipi-higher`）；级别**读不到** ⇒ 按 `block-integrity-unknown` 阻断，不假设它比我们低。只有显式 `--force` 才硬发（并打 `WARN=`）。来源：UIPI 的判定是"目标 IL 高于调用者 IL 就丢"，而读完不成时无法排除这个情形；载体：[机检] `decideInjection` 单测；[真机] 受限会话（`INTEGRITY_SELF=low`）对 Medium 窗口跑 `click`。
- **I9**：`INPUT` 结构体必须是 **40 字节**；字段**平铺**在 `INPUT` 上（`[StructLayout(LayoutKind.Explicit)]` + `[FieldOffset]`）；**绝对偏移的单一真相源是 C# 常量 `InputLayout`**（`Type=0`；鼠标视图 `MouseDx=8 MouseDy=12 MouseData=16 MouseFlags=20 MouseTime=24 MouseExtraInfo=32`；键盘视图 `KeyVk=8 KeyScan=10 KeyFlags=12 KeyTime=16 KeyExtraInfo=24`），依据是 Windows SDK 的 `WinUser.h`（本机 `C:\Program Files (x86)\Windows Kits\10\Include\10.0.22000.0\um\WinUser.h:6080-6129`）：union 含 `ULONG_PTR` ⇒ 8 字节对齐 ⇒ union 起点 8，`MOUSEINPUT` 里 `dwFlags` 前有三个 4 字节字段 ⇒ **20**，而 `KEYBDINPUT` 里 `dwFlags` 前只有两个 `WORD` ⇒ **12**。同一个双字在两个视图里位置不同，**共用一个字段名就会把键盘那侧的 `KEYEVENTF_UNICODE` 静默清零**。另有两类静态审查看不出来的静默致命后果：①**嵌套 union 里逐成员赋值**——PowerShell 对值类型的嵌套成员取到的是副本，`$item.u.mi.dx = 42` 写进被丢弃的临时对象，结构体全零送出、`SendInput` 照样报"已插入 N 个事件"、`GetLastError` 照样 0；②**平铺偏移写错**——同样无声失效（真机实测：完全权限会话里 `type --text ABCDEFGHIJ` 报 `INSERTED_EVENTS=20 CHARACTERS=10 CHANGED=false`，靶窗口内容一个字符都没进，而同一靶窗口用显式布局的 C# 发同样 6 个事件立刻出现字符）。所以事件一律由 **C# 工厂方法**构造（`Native.NewMouseInput` / `Native.NewKeyboardInput`，**PowerShell 侧只做像素归一化与 `[uint32]` 装箱，不许写任何结构体字段**），判据只能是**内存里的字节**：`probe` 用与 `Send-Inputs` 相同的 `StructureToPtr` 编码鼠标 / 键盘 down / 键盘 up / 滚轮四类事件，**并且同时**编一份 `WinUser.h` 原样的嵌套 union 参照结构体（`CANONICAL_INPUT`，只用于比对、不用于注入），逐字节比对必须相同（`MOUSE_MATCHES_CANONICAL` / `KEY_MATCHES_CANONICAL` / `KEY_UP_MATCHES_CANONICAL` / `WHEEL_MATCHES_CANONICAL`）。载体：[机检] `probe` + `test/injection.test.mjs`（钉死 12 个 `OFFSET_*`、三个 size 常量、`dwFlags == 0xc001`@20、键盘 `dwScan`@10 与 `keyFlags == 4`@12、keyup `flags == 6`@12、滚轮 `mouseData == 0xFFFFFE98`@16）；[真机] `INPUT_STRUCT_SIZE=40` 且注入真的改变靶窗口（鼠标与键盘两条路各一次，键盘要能被 UIA 独立读回）。
- **I9b**：`--dy` 为**负**时滚轮的 `mouseData` 是 `int32` 的 `-360`，必须以 **uint32 0xFFFFFE98** 进结构体（`MOUSEEVENTF_WHEEL` 在 `flags`@20，`dwData` 在 `mouseData`@16）。装箱走 `[BitConverter]::ToUInt32([BitConverter]::GetBytes([int32]($WheelDelta * 120)), 0)`：把 `-360` 直接给一个 `[uint32]` 参数，整条命令会在**造事件之前**死掉（真机实测原文 `Cannot convert value "-360" to type "System.UInt32"`，向下滚轮永远 exit 1、一个事件都没发出去）。载体：[机检] `test/injection.test.mjs` 的滚轮用例（`WHEEL_DW_DATA=-360`，同一批字节按 int32 读回来必须是 `-360`）；[真机] 见 `testing-guide.md` 的未观测项（读 `VerticalScroll.Value` 前后差）。
- 键盘注入前留 ~150 ms 稳定延迟（`--settle`，默认 150）、`type` 走 Unicode 逐字符注入。来源：本机实测 26 字符只落地 25 个，第 1 个丢在焦点转移窗口期；载体：[真机] `type` 后 `CHARACTERS=26` 且被 UIA 独立读回。
- `LAST_ERROR=` 必须在 `SendInput` 返回的**下一行**取样：`GetLastError` 是线程局部的、且成功的调用**不会清空**它，中间夹一次别的原生调用（`GetCursorPos`、`Add-Type` 的内部动作）就会留下一个陈旧码 —— 本机实测受限会话里 `move --force` 打的是 `LAST_ERROR=203`（`ERROR_ENVVAR_NOT_FOUND`），而同一行还写着"已插入 3 个事件"。这也是 I7 把它列进"只作诊断"的原因：它既不证明成功，也不证明失败。载体：[机检] `Send-Inputs` 的返回值形状（`{inserted, lastError}` 一次取回）；[真机] `move --force` 的 `INSERTED_EVENTS` / `LAST_ERROR` 两行与 `CHANGED` / `CURSOR_LANDED` 对照读。
- `--raise` 用 `SetWindowPos(hwnd, HWND_TOPMOST = -1, …, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW)`；不用 `SetForegroundWindow`（后台进程调它会被 Windows 直接拒绝，实测无效）。它**会永久改变用户的 z 序**，所以默认不开、由调用方显式要。**只对能指名窗口的命令有效**：鼠标类靠 `--x/--y`，键盘类靠 `--hwnd`；两者都没有时**不发事件、给一条 `WARN=`**（`cli.mjs` 的 `RAISE_NOTE`），绝不猜一个窗口；`--dry-run` 不报这条 WARN（没有"会不会生效"可言）。载体：[真机] `RAISED=true`。
- 键盘类命令另有一道**前台闸门**（`Focus-WindowForKeyboard`）：事件只会送到前台窗口，所以注入前先取 `GetForegroundWindow()`；目标不是前台就 `AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow` 重试；重试后**仍不是前台 ⇒ 报 ERROR、一个键都不发**（fail-closed）。目标窗口本身取不到（`--hwnd` 不是窗口、坐标处没有窗口、连前台窗口都没有）同样是 ERROR。来源：不这样做就会出现"发了 26 个字符只落地 25 个、第 1 个丢在焦点转移窗口期"这类半成功。**这道闸门只保证"收键窗口在前台"，不保证焦点在那个窗口的哪个控件上**：真机实测焦点停在 `Button` 上时 `type` / `key` 仍 `EXIT=0` 且 `FOCUS_OK=true`，而靶侧零新 `TEXTCHANGED`、CLI 报 `CHANGED=unknown`（诚实三态）。载体：[真机] 先让别的窗口占前台再 `type --hwnd <目标>`，输出 `FOCUS_OK=true`。

### VerifyState（可观测状态）

`{ foreground, foregroundTitle, windowCount, windowTitles, titlesDigest, point, pointTitle, pointProcess, pointIntegrity, pointRect, pointRootHwnd, pointLanded, pixelHash, contentRoot, contentHash, contentCount, contentBearingCount, contentReadings, contentNote, uiaAvailable, contentProbeFailed, contentKinds }`，摘要 `digestOf(state)` 是 `fnv1a32` 的 8 位十六进制（末尾带 `content=<hash>(<可读条数>)`）；`compareStates(before, after, { ignore })` 返回 `{ changed, reasons[], digestBefore, digestAfter, before, after }`，`reasons` 逐条写"哪一类判据变了"；`changeVerdict(cmp, { noPixel, needsKinds })` 把"有没有差异"翻成三态（I7b / I7f）。

`contentHash` 是**内容类判据**：读焦点元素 + `FromHandle(目标顶层)` + `FromPoint(--x/--y)` 三处的 UIA 属性（先无条件记一行 `identity|role|ControlType|Name`，再按可用性记 `content|role|value|…` / `rangeValue|…` / `scroll|垂直%|水平%` / `toggle|…` / `selected|…`）。读不到时 `contentNote` 里留原始异常文本（受限令牌下典型是 `point:Exception calling "FromPoint" …: "Access is denied"`），**不许静默吞**。这组读数**跑在独立子进程里**（`snapshot` 子命令，见 I7e）：UIA 的文本/几何方法能抛出 PowerShell `try/catch` 拦不住的 corrupted-state 异常，隔离之后一次崩溃只损失"这一次内容读数"，不会把整条注入命令带走 —— 此时 `CONTENT_PROBE=failed`、`contentProbeFailed=true`，该类判据降级 `unknown`；给了 `--no-content` 时探针没跑，这一格是 `CONTENT_PROBE=skipped`（外加一条说明覆盖面的 `WARN=`）。**文本选区故意不读**（原因见 I7e）。

- 五类判据：**前台窗口**、**窗口集合与标题**（`titlesDigest`）、**目标区域像素哈希**（`pixels`，`--no-pixel` 可关）、**`WindowFromPoint` 落点与命中窗口的完整性级别**、**UIA 内容快照**（`contentHash` + `contentKinds`，`ignore: [content]` 可关）。第三、五类都关掉、或这次动作要的那一类读数一条都没读到（I7f）时，`CHANGED` 只能是 `unknown`。前四类看得见"窗口层面"的变化，第五类才看得见"文本框里的字变了 / 列表滚了 / 勾选框翻了"—— 少了它就是 I7b 描述的那种假阴性。第五类跑在独立子进程里（I7e），它崩掉时这一类**整个退出差异集合**（缺测不是"没变化"）。
- **`point` / `pointRect` 两类判据必须从差异集合里剔除**（`compareStates` 的 `opts.ignore`，注入类命令传 `['point']`）。来源：`point` 是"这个坐标下现在是哪个窗口"，**光标一动它就变**，与目标窗口有没有收到事件毫无关系 —— 把它算进差异集合，注入失败也会报 `CHANGED=true`（真机实测出现过这种假成功：未抬顶时 `CHANGED=true VERDICT=changed` 而靶计数仍是 0）。落点改由独立的**落点归属**断言回答：`landingNote(state, target, req, { explicitTarget })` 比的是"落点窗口的**顶层**窗口是不是目标窗口的顶层窗口"（`LANDING=` / `LANDING_SAME_WINDOW=` / `LANDING_IN_TARGET=`，后者只在给了 `--target-hwnd` 时才给布尔，见 I7g），比 ROOT 不比叶子 —— 目标内部换个子控件不算跑掉。CHANGED 答"界面变没变"，它答"指针落在谁身上"，两者并列、互不代替。载体：[机检] `compareStates` / `landingNote` 单测 + [真机] 靶窗口计数。
- `--expect k=v;k=v` 的合法键就是 `EXPECT_KEYS`（`foreground` / `foreground_title` / `window_count` / `titles_digest` / `point` / `point_title` / `pixels` / `changed`），未知键报用法错。
- 像素抓取失败**不再静默吞**：`captureState` 返回 `{ state, pixelNote }`，抓不到就带一条 `WARN=像素抓取失败（Region=…）：…`，其余三类判据照跑。
- **I10**：`verify` 单独跑时 `CHANGED` 恒为 `false` 并打 `WARN=` 说明"没有'前'可比" —— 不许把它当成"没变化"的证据。载体：[机检] `cli-contract.test.mjs` 的用法错用例。
- **I10b**：`--dry-run` 时 `CHANGED` 恒为 `false` 并打 `WARN=` 说明"没有发送任何事件，这不是失败" —— 反之，**`--dry-run` 证明不了注入可用**。载体：[真机] `click --dry-run` 的输出 + `testing-guide.md` 的最小闭环。
- **I10c**：**CLI→桥 的参数映射是契约，`params` 就是全部输入。** `lib/bridge.mjs` 把 `params` 逐键翻成 `-Name value` 交给 `powershell.exe -File`；桥侧是 `param()` 显式绑定，所以**参数名写错会当场绑定失败**（不是静默的），而**"压根没写"是完全静默的** —— I7h / I7i 两个缺陷都属于后者。桥的 25 个参数：`Command Out Hwnd X Y Region Shot Hash Depth Name ElId ElRuntimeId SetValue Button Double Text Keys Clicks WheelDelta Limit NoMove MoveOnly PlanOnly Raise Invoke`。逐命令的实际映射（"CLI 下发"列是核对过的）：`profile` → `Command`；`screen` → `Command Shot Region Hash`；`windows`/point 换 `Command`；`uia` → `Command Hwnd Depth Name Limit ElId`；`point` → `Command X Y`；`probe` → `Command`；`verify` → `Command X Y`；`snapshot` → `Command Hwnd X Y`（加法见 I7h）；`invoke` 定位 → `Command Hwnd Name Depth Limit ElId`、动作 → `Command Hwnd Name ElId ElRuntimeId SetValue Depth Limit Invoke=true`（`ElRuntimeId` 是**可选**的：定位快照里那个元素有 `runtimeId` 才下发，没有就不发这个键 —— 桥侧缺省空串 ⇒ 不做身份复核，见 I6f）；`input` 的坐标类（`click`/`move`/`scroll`）→ `Command X Y Button Double Clicks MoveOnly WheelDelta`，键盘类（`type`/`key`）→ `Command Text|Keys Hwnd`，两类再统一挂 `Raise` / `PlanOnly`。桥声明而 CLI 从不传的三个是**登记项、不是缺陷**：`SetValue` / `Invoke` 只由 `invoke` 的定位与动作两次调用使用（已接线）；`NoMove` **目前无调用方** —— 它的语义是"一个事件都不发，只走构造与闸门判定"，而 `--dry-run` 已经覆盖了计划级预检、它的 UIPI 读数又是刻意的 `skip-dry-run`，再接线一条 `NoMove` 预检只会多出第三条功能重叠的路径，所以选择**保留桥侧的声明与分支、在这里注明无调用方**（真要临时用它，`params` 里加 `NoMove: true` 即可，桥的行为不用改）。载体：[机检] `test/params-map.test.mjs`（冻结桥的参数清单 + 逐命令核对函数体里必须出现的键 + 键盘路径必须有 `Hwnd`）；[真机] `--dry-run` 的 `PLAN_FOCUS_SOURCE=` / `PLAN_HWND=` 回显 —— 这是"CLI 到底有没有把 `--hwnd` 传下去"唯一不用发事件就能取的判据。
- **I10d**：**用不上的开关一律报用法错，不许静默忽略。** `COMMAND_FLAGS` 给每条命令一份开关清单（与 `COMMON_FLAGS` 合并后生效），`checkFlagScope(args, cmd)` 在分发前跑：不认识的开关 ⇒ `UsageError`（`<命令> 不认识开关：--a（这条命令认识：…）`）、退出码 **2**。来源：真机 `move --button right` 拿到的是普通移动、`type --x 5 --y 6` 悄悄丢掉坐标、拼错开关名（`--dryrun`）什么都不报 —— "传了参数"与"参数真的生效"被这一整类静默忽略分开了，两个 P1 就是靠它藏住的。`--target-hwnd` 只列在坐标类（`click`/`move`/`scroll`）的清单里：对 `type`/`key` 用它 ⇒ 报用法错（收键窗口是 `--hwnd`，I7i）。载体：[机检] `test/pure.test.mjs`（`checkFlagScope` / `allowedFlags` / 清单形状）+ `test/cli-contract.test.mjs`（五种"用不上的开关"各一条，断言 stderr 含"不认识开关""这条命令认识"）。

### 通信与部署形态

- **I11（通道）**：Node 与 PowerShell 桥之间**只用文件重定向**，绝不用 `stdio: 'pipe'`。受限令牌下 libuv 的命名管道对限制 SID 没有写权限 ⇒ `spawn(..., {stdio:'pipe'})` 直接抛 EPERM。实现是 `runBridge` 里 `spawnSync(powershell, args, { stdio: ['ignore', stdoutFd, stderrFd] })`，`-Out` 指到一个 `%TEMP%\adg-desktop-*` 临时目录里的文件，**成功与失败都删**（`runBridge` 的 `finish()` + 异常路径，`bridgeJson` 再兜一层）；只想排障时传 `keepFiles: true`。同一理由让 `node --test` 在沙箱里必须加 `--test-isolation=none`。载体：[机检] `cd desktop && node --test test`（受限会话下不加 flag 会 EPERM，加了就全绿）+ 跑三条命令前后 `(Get-ChildItem $env:TEMP -Directory -Filter 'adg-desktop-*').Count` 不变。
- 桥的契约：一次进程一个子命令（`profile` / `screen` / `windows` / `uia` / `point` / `input` / `verify` / `snapshot` / `probe`），把**一个** JSON 对象写进 `-Out`（UTF-8 无 BOM）；Node 侧只解析这个对象，stdout 不承载数据。
- `probe` 是**只做内存编码**的诊断子命令：构造鼠标事件、键盘 down / up、滚轮事件各一个（滚轮用 `-3` 格，即 `mouseData = 0xFFFFFE98`，见 I9b），`StructureToPtr` 出来后回传十六进制字节、字段读出与 12 个偏移常量，**从不调用 `SendInput`**；同时编一份 `WinUser.h` 原样的嵌套 union 参照结构体做逐字节比对（见 I9）。它存在的唯一理由是 I9 的那两类缺陷（结构体全零 / 偏移错位，两者都照样报"已插入 N 个事件"）静态审查看不出来，判据只能是原始字节。
- `snapshot` 是**只读内容、零副作用**的诊断子命令（作用域是**加法**的：`--hwnd` 钉根、`--x/--y` 加读落点与 3 层祖先，两个都给了就都读；都没有才退回前台窗口，见 I7h），单独占一个进程是刻意的：它是唯一会向 UIA provider 要文本/几何读数的地方，而这类调用能抛出 `try/catch` 拦不住的 AV（I7e）。它**不** `Send-Inputs`、**不** `SetForegroundWindow`、**不** `Raise-Window`、**不** `AttachThreadInput`（有静态守卫测试钉住），所以随时可以单独跑它来确认"这条读数现在不会把进程打死"。
- `bridge.mjs` 侧固定项：`MODULE_ROOT`、`BRIDGE_SCRIPT = <模块根>/scripts/bridge.ps1`、`DEFAULT_TIMEOUT_MS = 60000`、`resolvePowerShell(env)`（`ADG_DESKTOP_POWERSHELL` 覆盖 > `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` > `pwsh`）。**另一条同类缝隙**：`cli.mjs` 的 `bridgeOpts(args)` 认 `ADG_DESKTOP_BRIDGE=<脚本路径>`，把这次调用的桥换成**另一个文件**（测试与排障用；与 `ADG_DESKTOP_POWERSHELL` 同口径，未设时就是 `BRIDGE_SCRIPT`）。它存在的理由具体：I6f 的身份复核发生在桥的**第二遍遍历**里，不给这条缝隙，"两次遍历报到不同的 runtimeId"就只能靠真机竞态复现 —— 有了它才能用一份罐装 JSON 的假桥把 `mismatch` 那条路钉死在机检里（`test/element-identity.test.mjs`）；`runBridge` / `probeBridge` 本来就有 `opts.script`，这里只是把它接到环境变量上。
- **元素身份判定单列一个文件**：`scripts/identity.ps1`（`Get-ElementIdentityGate`，见 I6f）。它只做一件事：`$Expected -eq ''`（没给身份 ⇒ 老调用方式）或 `$Actual -eq $Expected`（一致）就 `return $null`（不拦人），否则返回那份 `identityMismatch` 报告。**单独成文件的理由是"可被同一份代码引用"**：`scripts/bridge.ps1` 用 `. (Join-Path $PSScriptRoot 'identity.ps1')` dot-source 它，`test/fixtures/invoke-identity-bridge.ps1` 用 `. (Join-Path $PSScriptRoot '..\..\scripts\identity.ps1')` dot-source **同一份** —— 会执行的那条用例跑的因此是真判定，而不是假桥里另抄一遍的副本。来源：对抗性验收实测 —— 把桥里那段内联判定的条件改成 `if ($false -and …)`（字面量全留）**151 条测试全绿**，因为假桥自己重写了一份判定、只读源码的守卫又只看字面量在不在。同一处还有第二个缺口（G1）：静态守卫原先只钉住闸门**调用点**在动作之前 —— 把**拒绝块**挪到 `Do-InvokeChosen` 末尾（调用点不动）时，判定仍会"检出"却不再"拦住"，而所有"在 gate 之后"式断言照样为真、两个测试文件全绿；现在两条守卫都另外要求拒绝块的三段位置（`if ($null -ne $identityGate) {` / `Write-Report $identityGate` / 紧随的 `return`）都早于**第一个**动作原语，并且每条断言先要求 needle 存在（`at > 0`），免得 `indexOf` 的 `-1` 把"缺失"读成"合格"。只补"三段各自在动作之前"还有一道缝：`return` 那一针取的是"拒绝块之后的下一个 `return`"—— 而 ValuePattern 失败分支里也有一个 `return`、它本来就在第一个动作原语之前 —— 于是把拒绝块**自己的** `return` 删掉、或只把 `Write-Report $identityGate` 搬到函数末尾，三针都还是真的；所以另用一条正则把这一块钉成**连续的一段**（`if ($null -ne $identityGate) {` / `Write-Report $identityGate` / `return` 之间只许空白），并要求整段位置早于第一个动作原语。三种变异（整块后置 / 删掉块内 `return` / 只搬走 `Write-Report`）现在都红这两个文件：各 `15 tests / 13 pass / 2 fail`、退出码 1。**但这些守卫保证的是源码文本层面的位置关系，保证不了这段文本会执行** —— 第 3 轮复核实测的 M6 就是反例：把闸门**调用语句**与拒绝块**一起**包进恒假 `if ($false) { … }`（文本一字未动）时，两个文件 `15 pass / 0 fail` 全绿，而运行期这道闸门已经死了。H1 之后新增的最低文本条件是两条：①拒绝块的**紧邻上一条非空源码行**必须就是闸门调用语句（中间夹一层恒假 `if` 或夹一句注释 ⇒ 这块不会执行）；②闸门调用语句与拒绝块之间不许出现 `if (` / `while (` / `foreach (` / `switch (` / `<#`，也不许有行首 `#` 的注释行；再加一条"那三行必须独立成行、行文本精确相等"（行首 `#`、行尾注解、被包进别的 `if` 都在这里红）。实测**挡得住**（都变红）：拒绝块后置、删块内 `return`、搬走 `Write-Report`、在调用与拒绝块之间插任何**非空**行（恒假 `if` / `<#` / 行首 `#`）—— 插**纯空行**不算（第 4 轮复验实测仍全绿）、改动那三行的行文本；**挡不住**（静态文本守卫判不出"不可达性"与"作用域语义"；**以下为已实测的形状，非穷举** —— 未在假桥/静态层可覆盖的不可达与作用域变体仍可能存在）：把调用与拒绝块一起包进恒假或不可达分支（M6 `test/element-identity.test.mjs`（D108）+ `test/params-map.test.mjs`。
- **平台闸门**：`WINDOWS_ONLY = true`、`platformVerdict(platform)` 在非 `win32` 时返回一句人话原因；`cli.mjs` 在 `profile` 之外的命令上直接抛错（退出码 1），`profile` 打印 `PLATFORM=` / `WINDOWS_ONLY=false` + `WARN=` 且**不 spawn 桥**。

## 对外接口

### 命令行契约

**`node cli.mjs help` 是命令与选项的唯一真相源**，本文件不复制选项表（`desktop/AGENTS.md` 的速查表也只是索引）。约定：

- 命令是第一个非 `--` 参数；`--k=v` 与 `--k v` 等价；`BOOLEAN_FLAGS`（`json` / `double` / `dry-run` / `force` / `fallback-point` / `raise` / `no-pixel` / `no-content` / `hash` / `help`）**绝不吞下一个 token**（否则 `--json windows` 会把 `windows` 吃成 `json` 的值）；反过来，`REQUIRES_VALUE` 里的开关**缺值当场报用法错**，不静默变成 `true` —— 静默变 `true` 会让报错点跑到坐标层，离用户的输入太远。这两份清单是这条判定的**单一真相源**。
- 用法错（不认识命令、缺值、越界、非法枚举、多余位置参数、`screen --out` 的**父目录不存在** —— 本模块不替调用方建目录）走 `UsageError` ⇒ stderr 打 `ERROR=<msg>` + **一行**`提示：node cli.mjs help 看完整用法。`，退出码 **2**（不再吐整屏 USAGE —— 那会把真正的报错顶出视野；完整用法属于 `help`）；运行期错误 ⇒ stderr 打 `ERROR=<msg>`，退出码 **1**；成功 **0**。
- `invoke` 的失败分两种，**都不许报成功**：元素不支持任何可用 pattern（或 `--set-value` 遇到不可用的 `ValuePattern`）⇒ `UsageError`、退出码 **2**；元素与 pattern 都在但**调用抛了**（`OK=false`）⇒ 打 `WARN=` 说明"语义操作没有真正生效"、退出码 **1**。
- `invoke` 还有第三种失败，**它连动作都没执行**：**元素身份复核不一致**（`ID_IDENTITY=mismatch` —— CLI 把定位快照的 `runtimeId` 作为 `ElRuntimeId` 下发，桥在**动手路径的任何动作原语之前**发现这次命中的元素报的 runtimeId 不同）⇒ 桥 `invoked=false`、`patternError='element identity mismatch: id matched but runtimeId differs'`，CLI 打 `WARN=元素身份不一致…` 后走 `UsageError`、退出码 **2**。**与上面那条 1 的分界**：**1 是"动作执行了、但没生效"（要查闸门与靶侧），2 是"拒绝动手、一个事件都没发"（要重新取 id —— id 命中不证明是同一个元素）**；两种都"不许报成功"。见 I6f。
- `--json` 时在 `KEY=VALUE` 之后**额外**打一行 `JSON=<对象>`；`KEY=VALUE` 永远照打，机器可读与否都不改变人可读的输出。

### 判据怎么取

所有读数**当场取**、不作锚：屏幕尺寸与虚拟屏原点来自 `GetSystemMetrics` / `EnumDisplayMonitors`（在 `profile` / `screen` / 注入命令的 `VIRTUAL_*` 行里各取一次）；自身与目标的完整性级别来自令牌的 `TokenIntegrityLevel`（每次现读，读不到就是 `unknown`）；`CHANGED` 来自动作前后两次 `VerifyState` 的比较。`INSERTED_EVENTS` / `LAST_ERROR` / `INPUT_STRUCT_SIZE` 只是**诊断**，看它们不能判定成功；其中 `LAST_ERROR` 还必须是 `SendInput` 返回后立刻取的（见 InjectionPlan 一节）。

## 非功能红线

1. **不假成功**：注入类命令没有可观测变化时输出 `CHANGED=false` + `WARN=`（写明"可能是 UIPI 静默丢弃"），不因为 `SendInput` 返回了数字就报成功。`--dry-run` 与单次 `verify` 的 `CHANGED=false` 都带 `WARN=` 说明"这不是失败/没有可比的前"。
2. **不越权**：不绕 UAC、不碰安全桌面、不做进程注入、不改系统设置、不驱动管理员权限进程（见「职责与边界」的"不负责"逐条）。**完全权限只解降权，不获得管理员权限** —— 实测完全权限下令牌的完整性级别是 `S-1-16-8192` (Medium)、`TokenRestrictedSids` 空（neededBytes=8 / Count=0）、`TokenElevationType=3` / `TokenElevation=0`、Administrators 仍 deny-only、无 `SeDebug`。High 完整性级别的管理员窗口与 UAC 安全桌面依旧够不着。
3. **零依赖、零安装**：不引第三方包，不下载任何东西，不改用户的环境变量与系统设置。`bridge.ps1` 的临时文件只写在 `%TEMP%` 且用后即删。
4. **受限与完全权限两种会话都要能跑**：通道走文件重定向（I11），失败要如实报 EPERM 而不是降级成 pipe 重试。`bridge.ps1` 保持 ASCII-only 无 BOM。
5. **`--force` 不改变判据**：它只跳过闸门（UIPI 完整性级别、以及坐标类命令的几何自洽检查 `GEO_MISMATCH`），注入后的观测与 `WARN=` 一样照跑照打；不许把"用了 `--force`"当成成功，跳过几何闸门时那条 `WARN=` 必须保留在输出里。
6. **`--raise` 副作用显式**：它改变用户 z 序，默认关闭，只在调用方显式要求时使用。
