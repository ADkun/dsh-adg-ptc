# 把方案烤一遍（Adg 版 grill-me）

访谈一件事直到**共识**：不把任何一处含糊留在「我以为」。这份技能是**给调度智能体自己**用的 —— 它管「问什么、查什么、什么时候算问完」，不管派谁干活。

## 设计树、前沿、轮

- **设计树**：把主题画成一棵决策树 —— 每个决策分出挂在它下面的决策。
- **前沿**：前置条件都已经定下的那些决策，也就是**现在就能问、不用猜用户还没说的答案**的那些。
- **一轮**：一次把**整个前沿**问完（每问编号 + 附推荐答案），然后**停下等用户答复**。用户这一轮的答复会让前沿外移、解锁下一层 —— 重算前沿，再问下一轮。
- **被本轮未决问题挡住的问属于下一轮**，不要提前问。

## 每问的格式

```
❓ **Q1** - **<问题标题>**：<问题正文 —— 可以多段，可以列多个选项>

➡️ <你的推荐答案>
```

每问都要带推荐答案：推荐是你基于**已定决策**给出的判断，用户可以直接采纳。

## PTC 下怎么问、怎么查（先读这一节）

本 preset 是 PTC 呈现：你的目录里**只有 `run_code`**，直呼 `ask_user_question` / `read` / `web_search` 会解析成 `UNKNOWN_TOOL`。两件事的写法变了，判据没变：

- **问用户**：`const ans = await tools.ask_user_question({ questions: [...] })` —— 一次把整个前沿问完、相关的几问一次问齐。**这一问等回答时占着那段 `run_code`**（时限含等待，当前值见 `run_code` 的 `timeoutMs` 说明），所以：①单独成段，别和查证调用挤在一段程序里；②一次问全，不要一问一段程序；③万一程序在答复到达前结束，那个问题可能收不回来 —— 重新问一次，别当成用户已答。
- **查事实**：`await tools.read(...)` / `tools.glob(...)` / `tools.grep(...)` / `tools.pwsh(...)` / `tools.web_search(...)` / `tools.web_fetch(...)`，无依赖的用 `Promise.all` 并发；**只 `return` 结论与位置锚**，不要把整份文件、整页搜索回灌进上下文。
- **派子代理**：`await tools.delegate({ description, prompt, tools })`（见下节）。

## 谁答什么：事实归你，决策归用户

**事实**是环境里查得到的东西，查它是你的活，不是用户的活：仓库 / 本机文件用 `tools.read` / `tools.glob` / `tools.grep` / `tools.pwsh`；公网用 `tools.web_search` / `tools.web_fetch`（都在 `run_code` 里）。一两次嵌套调用能答完的自己答 —— 为一次抓取派子代理要多付一整个子代理的固定开销。

**要子代理查才值得的**（成片调研、多源交叉、要独立视角）走 Adg 唯一的委派入口 `delegate`（在程序里 `await tools.delegate({...})`），写法照 `adg-delegation` 的 ④ 全网检索 / ⑤ 本地检索两条能力带：`tools` 给 `['read','glob','grep','web_search','web_fetch','notify_user']`（⑤）或 `['web_search','web_fetch','notify_user']`（④），**不要设 `background`**（缺省就是后台 continuable），`prompt` 里写清要它答**哪几个具体问题**、每条结论带可复核的位置锚。

**硬判据（这份技能存在的原因）**：Adg 里**没有**「顺手在后台起了个调研子代理」这种不留痕的事 —— 只有真的调用了 `tools.delegate`、拿到返回的 `subagent_id`，才算派过。没调就不许在回答里写「我已派子代理去查」：要么当场调，要么把这件事写成「未查」。坏形态就是：声称后台派了调研子代理，而 `await tools.list_agents({})` 里什么都没有。

**不要为调研阻塞**：正在跑的调研是**未定的前置**，只有它下游的问题等它报回；本轮其余前沿照常问。

**决策是用户的**：每一条都要交给用户并等答复。**你自己**用 `tools.ask_user_question` 在本会话里问（平台这条工具只认 live runtime root，调度者就是它认的那个活 root）；被派出去的子代理要问人则用 `adg-delegate` 的 `ask_user` —— 那一问以**派它的调度者**（也就是你）为 owner 进提问服务，卡片落在你这个会话里，用户答完答复直接回到它手上。所以**要用户拍板的问题一律由你在本会话问**，不要塞进任何一次委派的 `prompt`。

## 提问通道

默认**在正文里按上面的格式问**：一轮前沿常有多个多段问题、还要列选项，硬塞进选项框会丢信息。一轮里只有少数几个**互斥选项**、或用户明显想快点选时，改用 `ask_user_question` 把这几问做成选项（相关问题一次问齐）。

两条路都遵守同一条纪律：**问完就停手等用户答复** —— 不自问自答、不替用户挑「最省事的解释」。人工介入不设次数上限，只有用户自己说过「别问我」才停手并如实报出未决项。

## 一次一题

用户说「一次问一个 / 别一次问一堆」时切到逐个问：走进决策树每条分支，一次只问一个、等反馈再问下一个 —— 一次问一堆对他是负担。其余口径（推荐答案、事实自查、决策归用户、共识后才动手）不变。

## 什么时候算完

前沿为空 = 设计树每条分支都走到了、没有一处是「默默假设」的。此时**先与用户确认共识**；用户确认之前**不许动手** —— 访谈期间只许为查事实派只读调研委派，不许派执行型委派（写文件 / 改系统 / 上网操作）。

## 与 Adg 的分工

- 本技能是**调度者自用**的：不要再把这份文件的路径转给子代理，子代理需要的是 `adg-delegation` / `adg-browser-use` / `adg-computer-use` / `adg-file-ops`。
- 访谈进行中你仍然只做调度与汇总：不碰文件、不改系统设置、不操作网页（唯一例外仍是「中转材料」允许的平台临时目录）。
- 共识达成后的落地照常走 Adg 的委派流程（按能力带现给 `tools`）。

## 未观测

- **未观测**：一轮问 5 个以上问题时用户的实际答复率与跳答率（本技能只按「一次问齐前沿」描述，未量化）。—— 量法：记几次访谈里每轮的题数与被跳过的题数，看是否该为超长轮次另给分轮策略。
- **未观测**：DSH Web 里「正文提问」与「`ask_user_question` 选项」两种通道下用户答复的完整度差异。—— 量法：同一主题各跑一次，对比用户对每个问题的答复是否逐条覆盖。
