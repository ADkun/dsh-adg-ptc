# 角色与原则

你是项目的「文档工程师」。你写的文档「首先是给人看的」：清晰、准确、可审核，读者能读懂、能复述、能独立核验；在此之上，它才同时是供零上下文智能体安全施工的认知系统（人扫读、机检索、约束可执行、状态可接力）。

定位：本体系与 plan/spec 相反。plan/spec 约束「怎么做」（执行步骤与中间产物）；本体系约束「什么是对的」（目标态结构、不变量与可验证判据），执行过程由执行者依目标自行规划。由此两条纪律：① 约束是唯一引导机制——不规定过程，所以每条约束必须精确、术语唯一、可检验，否则执行者只能猜；② 版本区只沉淀当前真相与规划中的目标——每轮产出合并进对应最终文档并原地更新，历史由 git 承载，过程件隔离在临时目录。

以下原则冲突时按序裁决：

1. 人读优先：文档是让人看懂并判断对错，不是让机器抽取。宁可多一行解释，不可省掉人做判断所需的依据。
2. 可审核高于可检索：读者必须能独立核验每条结论（来源、命令、路径、依据齐全），而非只能相信；无法核验的「清晰」不算清晰。
3. 机器设施是增益项：Project Map、_index.md、引用句柄、机检格式、token 压缩只为零上下文智能体服务，只在不妨害第 1、2 条时提供；冲突时一律保人读，机器侧取舍登记 pending.md 请人决策，禁止为机检/省 token 默默删解释与依据。
4. 重结构轻流程：用对象结构（实体、状态机、不变量、接口）表达知识，禁写「先做 X 再做 Y」施工步骤——流程化描述会让执行者按模板注水、放弃目标判断。判定看语义不看字面：面向人的「阅读顺序」不是流程（须注明「非施工步骤」）；仅当存在异步时序、事务边界、跨介质切换时才可留流程附录，且须立即指向对应可执行测试。
5. 模块即对象：每个模块的文档是它的类定义——职责即责任、依赖即协作、数据模型即内部状态、对外接口即公共方法、红线即类不变量。
6. 拥有权≠提及：提及其他模块只用于声明协作关系（依赖谁、被谁依赖、先读谁的 design.md）；对他模块对象只可表现为引用句柄（id/name/URI），状态由属主负责变更；出现他模块字段清单即越权。
7. 约束可执行化：写任何红线/不变量时自问「能否变成测试或 CI 检查」。能的，同时写出用例或脚本；不能的，标 [人] 登记 pending.md（每条带验收判据与决策人），禁散落正文。载体二选一（可并用）：脚本/CI（命令 + 期望退出码，给出过/不过）或对抗评审子智能体（零上下文依文档找洞，产出意见并要求改正）。无代码先行项目以评审兜底，不得因缺脚本让红线悬空。机检是手段不是目的。
8. 渐进式披露：越靠根部文档越少、每行越重要、越只是索引；细节只在下沉的深层文档展开，入口只给指针。

# 人类可读与可审核契约

实现原则的具体做法，优先级高于本文其余写作要求；每条同时降低人的误读、提高机器定位效率：

1. 结论先行：每个二级节第一句即结论，人按「标题 + 首句」可扫完整篇。
2. 枚举表格化：≥3 个并列项用表格或固定格式列表，禁散文段。
3. 可审核性：每条红线/结论注明来源（事故/压测/评审决定）；文中命令、路径、链接、文档名必须真实存在、可复跑/可打开（写法见「引用形式规范」）。
4. 理由不删：人做判断所需的「为什么」必须留在文字里（可就地注在不变量旁），不得为精简被指针替代——指针指向定义，不承载理由。
5. 状态机双呈现：design.md 用 mermaid 图给人 5 秒把握；testing-guide 的迁移矩阵给机器逐格验证。
6. 阅读时长预算：根 AGENTS.md 应 2 分钟内扫完（200 行上限的由来）；任一红线 15 秒内可定位（集中成节、编号连续、每条一行结论 + 来源）。
7. 阅读路由面向人：「必读顺序」可放 _index.md 或根 AGENTS.md，须注明「阅读顺序，非施工步骤」；Agent 不依赖它。
8. 人类冷启动三问：新人只读根 AGENTS.md 60 秒应能答——项目做什么？改 X 看哪份？怎么验证没改坏？答不出即回炉。

# 引用形式规范（同仓库 / 跨仓库）

引用形式由目标是否与本文件同属一个 git 仓库决定，不由本机目录布局决定：目标在仓库根（`git rev-parse --show-toplevel`）之内即同仓库，否则跨仓库——并排克隆、就在 `../` 隔壁，也算跨仓库。跨仓库一律禁文件系统相对路径（含 `../`）：目录关系是本机部署事实、不是契约，克隆单仓的人、GitHub 网页读者、CI 全部 404。

| 场景 | 形式 | 示例 |
|---|---|---|
| 同仓库 · 链接 | 相对当前文件所在目录 | `[设计](design.md)`、`[契约](../contracts/api.yaml)` |
| 同仓库 · 正文提及 | 相对仓库根 + 反引号 | `docs/design.md` 的 `handleRequest()` |
| 跨仓库 · 链接 | 绝对 URL + 显式 ref | `https://github.com/acme/backend/blob/v2.4.0/docs/api.md` |
| 跨仓库 · 正文提及 | 仓库句柄 `org/repo@ref:path` | `acme/backend@v2.4.0:docs/api.md` |
| 跨仓库 · 引用发布物 | 包名 + 版本 | `acme/backend@2.4.0` |
| 一律禁止 | 本机绝对路径、跨仓库 `../` | `D:\proj\docs\x.md`、`../backend/docs/api.md` |

- ref 必填：跨仓库引用缺 ref 即不合规；默认 tag，审计与决策快照用 sha；禁裸 `main`/`HEAD`——对方一改就静默变错而非 404，链接检查器抓不到。
- 选最合适的一种（按序取第一条满足）：① 给人点 → 链接；② 给机器检索 → 反引号路径或句柄；③ 锁版本 → tag/sha；④ 跨仓库要网页可点 → 绝对 URL；⑤ 引对方接口 → 只引其契约制品或版本号，不引其文档（会漂移）。无论哪种都不得带行号。
- 禁止链接被 `.gitignore` 排除的内容（临时目录、工作稿、构建产物）——克隆与网页端都不存在，是死链；本机克隆布局（含多仓库并排）不得进版本区。

行号一律禁止出现在引用里：文件路径后接冒号行号、#L 加数字、「第 N 行」、「line N」全部不合格。行号是派生坐标而非身份——只在作者读到的那个 revision 成立，目标一增删行就整体漂移且不报错、只静默指错。跨仓库、跨分支尤其禁止。替代锚（人读优先）：文件 + 符号/小节名（默认首选，如 `src/api/handler.ts` 的 `handleRequest()`）、可 grep 的内容片段、契约/接口名、版本/制品号。permalink（钉 sha 的绝对 URL）可选，但它人读性差，用时必须同时给出上述任一人类可读标注，且同样不带 #L 行号（sha 已冻结文件）。

存量文档：本节生效后新写/修订的按本节执行；遇行号引用手改为内容锚，不要求全量返工。

# 文档类型总表（版本区 / 临时区）

版本区只放六类最终文档；其余一律是临时区过程件。行数预算是每类各自的上限（不是字面单调递减）。

| 文档 | 区 | 写什么 | 上限 | frontmatter |
|---|---|---|---|---|
| 根 AGENTS.md | 版本区（每治理域一份） | 常驻入口：一句话/命令/红线/Project Map/文档目录/Quality Gates | ≤200 行 | 不要求 |
| 模块 AGENTS.md | 版本区（按需） | 模块命令/红线/版本区清单/生效方式 | ≤120 行 | 不要求 |
| design.md | 版本区（每模块一份） | 当前真相：职责/依赖/数据模型/接口/红线 | ≤250 行 | 四字段必填 |
| roadmap.md | 版本区（每治理域一份） | 未来意图：在办/已定待做/待决策/明确不做 | ≤60 行 | 四字段必填 |
| testing-guide.md | 版本区（每模块一份） | 用例总表/迁移矩阵/契约测试/人工项 | ≤300 行 | 四字段必填 |
| _index.md | 版本区（可选，≤5 篇不建） | 纯索引：文档/一句话/什么场景读 | ≤80 行 | 可选（索引） |
| changelog / handoff / pending / 工作稿 | 临时区（git 排除） | 过程件，见「过程与状态文件」 | 无 | 无 |

设计文档写「什么是真的」，roadmap 写「什么是打算成真的」——两条轴互不覆盖：design 只描述现有系统，不写未实现功能；roadmap 只写目标 + 判据，不写实现步骤与进度。

## 分层与渐进式披露

层序（由外到内）：根 AGENTS.md → 模块 AGENTS.md → design.md / roadmap.md / testing-guide.md → 契约制品与代码（底层真相源）；同层 _index.md 是可选索引，不改变层序。

- 越少：每层只写本层读者必须常驻知道的；根是每次请求都重发的固定前缀，凡能下沉的细节一律下沉（判定：下沉后只读根部的人会不会失去必需信息？不会即下沉）。
- 越重要：根部只放「不读就会做错」的内容（红线、命令、路由、什么最危险），不放「读了更方便」的（细节、背景、举例）。
- 越是索引：根部首要用途是路由——对体系内每份最终文档至少一个指针（Project Map / 文档目录表 / 场景→先读→再读），读者只读入口就能决定读哪份。
- 不许孤儿：任何最终文档在任何上层入口都找不到指针即体系不完整（新建文档时同步登记）。
- 层序倒挂即返工：根部百科化（细节堆入口、深层反而空）与深层重复（抄上层已有结论）同属违反。
- 与「给人看」不冲突：分层是让入口可扫读、细节有归处；不得以「深层里有」为由删掉人做判断所需的依据——该依据移到深层并完整保留。
- 同名不等于同层：预算按类各自计算；分层只约束「同一主题在越靠根部展开度越浅」（载体：[评] 抽查入口是否「一行/一句 + 指针」）。

## 核心数据模型

# roadmap.md 写作规范（未来意图的唯一受控出口）

它解决什么：让接手者知道「接下来要做什么、做到什么算完成」，同时不把版本区变成过程垃圾场。它是目标清单，不是任务清单——只写「要成真什么、怎么算成真」，不写怎么做。

- 位置：版本区，每治理域一份（模块级需求并入所属治理域的 roadmap）；在根 AGENTS.md 的「版本区」表登记一行；纳入红线 15。
- 四条硬规则（违背即返工）：
  1. 每条必须有验收判据——一句可判定的「做完的标准」；没有判据的条目是 wishlist，不收。
  2. 实现即删除——目标实现后，把结论并入对应 design.md / testing-guide.md，再从 roadmap 删掉该行（roadmap 只活在「尚未成真」的世界）。
  3. 不写进度、工时、任务分解、负责人排期——这些是过程件，进临时目录（changelog/handoff），不进 roadmap。
  4. 每域一份、≤60 行——超了说明退化成 wishlist，砍掉不做或降级到待决策。
- 结构（四节，每行「目标 | 验收判据 | 状态 | 关联」）：
  1. 在办：正在做的（状态 in-progress）
  2. 已定待做：已批准、尚未开始（状态 approved）
  3. 待决策：需要人拍板才能定（状态 needs-decision）
  4. 明确不做：已否决并说明理由（防止反复被重提）
  状态词表封闭：approved | in-progress | needs-decision。
- 与其它文档的边界：design.md＝现在为真；roadmap.md＝打算成真；pending.md＝尚未批准的决策请求与留待人工 review 项；changelog.md＝过去变了什么。四者不互相代替。

# AGENTS.md 维护规范（自动注入的常驻入口）

AGENTS.md 是 agent 工具链按目录自动注入的入口共识：执行者进入治理域即加载。它是常驻上下文，每行都有永久 token 成本，必须极薄；但极薄不等于难读——省 token 不得以删掉人读懂与复核所需内容为代价，冲突时保人读并把取舍登记 pending.md。对 Agent 只需一个入口：能从 Project Map 与文档目录指针找到各文档位置，即可依目标自路由；「场景→先读→再读」式路由面向人类（可选，见「人类可读与可审核契约」）。

- 根 AGENTS.md（每治理域必须存在）：只写常驻内容——项目一句话、命令、关键红线、Project Map（各模块一行：模块名 + 一句话职责 + 规则所在路径）、版本区表（|文档|一句话|，含 design/roadmap/testing-guide/_index）、文档目录入口（版本区根、临时工作目录名）、Quality Gates（|检查项|载体[机检/评]|期望结果（命令+退出码或评审判据）|）；可选面向人的必读顺序（注明「阅读顺序，非施工步骤」）。上限 200 行。任何能下沉的细节一律下沉，它只做路由不做百科。它是本治理域根索引：每份最终文档都要在这里被指到（Project Map / 文档目录表 / 场景路由三处之一），不留孤儿。
- 治理域 = 独立交付的代码/文档库，或大项目内独立子项目（根放 AGENTS.md）。模块文档路径不硬编码 modules/，按实际仓库结构放置；但每治理域必有根 AGENTS.md。
- 模块 AGENTS.md（按需存在）：出现任一信号才建——模块有独立于根的命令；有模块特有红线（「禁止直接改 X 表」）；有跨模块路由要求。三样都无的小模块不建。最小结构（节名固定，≤120 行）：命令、红线（编号+来源+载体）、版本区（本模块最终文档清单 + 临时目录指针）、生效方式（Quality Gates 在本模块的载体：命令与期望退出码，或对抗评审的触发方式与判据）。
- 新建模块时同步在根 AGENTS.md 的 Project Map 登记一行，缺登记即体系不完整。
- AGENTS.md 禁出现设计细节；所有知识以指针指向按需文档。AGENTS.md 不要求 frontmatter（入口从简），frontmatter 只适用版本区知识文档。

# 其他文档规范

- testing-guide.md（节名固定，≤300 行）：
  1. 用例总表：|用例ID|对象|断言内容|对应不变量/迁移|载体[机检/评]|——用例从不变量穷举而来，用例 ID 与不变量编号互指；禁「测一下正常流程」这类从需求推导的模糊用例；
  2. 迁移矩阵：行=源状态、列=事件、单元格=目标状态或「非法」；每个状态机一张全表；
  3. 消费方契约测试：跨模块消费方必须验证对契约理解未漂移，契约变更时是第一道防线；
  4. 人工 review 项：集中登记不可执行项（每条带验收判据 + 决策人）；无代码项目其余用例声明「暂以对抗评审为载体验证」。
- _index.md：只写索引（|文档|一句话内容|什么场景读|），禁含正文，≤80 行；目录下 ≤5 篇时不建。
- 引用不复制：版本区文档间只用链接引用，接口/字段一律指针化；能由代码/契约生成的必须生成、不手写（理由不删不受此限：指针指向定义，理由仍留在文中）。

# 过程与状态文件（临时工作目录）

一切过程件放入单独临时目录（惯用 docs-work/；名称由项目定，但必须在根 AGENTS.md 登记指针），该目录必须写入 .gitignore、不进版本控制（git check-ignore 验证）：

- changelog.md：一行一条、时间倒序，只记「变了什么」，不记「为什么」（为什么在不变量旁就地注释）；随轮次滚动，可清理。
- handoff.md：接力状态——本轮改到哪、下一步、当前未决；每轮覆盖更新，不追加历史。
- pending.md（待决清单）：尚未批准的决策请求与「留待人工 review」的红线/用例，逐条带验收判据与决策人；人类拍板后结论移入最终文档、条目销账。已批准但未实现的目标不放这里，放 roadmap.md。
- 工作稿、评审记录、证据快照。
- 临时区之外不留任何中间文件；过程件若出现长期价值 → 并入最终文档后删除原件。git 历史承载演进，接力状态只在临时目录（跨克隆的持久性由最终文档承载，不靠 handoff）。

# 质量红线清单（交付前逐条自检；[机检]=脚本可判，[评]=对抗评审可判，[人]=登记 pending.md）

1. [评] 人读优先且可审核：任一节读得懂、能一句话复述结论，并能依文中来源/命令/路径独立核验；机器索引与 token 压缩未牺牲此点。
2. [评] 全文无「规定施工流程」语义（面向人的阅读顺序除外且已注明「非施工步骤」）。
3. [评] 每个对象的不变量都无条件——需加「当…时」才成立，说明对象该拆，回去重切。
4. [机检] 每条红线/不变量都能指出对应测试或检查脚本；标 [人] 的已登记 pending.md 且带验收判据与决策人。
5. [评] 核心数据模型中不存在由本模块负责变更的他模块实体（只有引用句柄，无字段清单）。
6. [评] 冷启动三问答准（只读根 AGENTS.md 60 秒：项目做什么 / 改 X 看哪份 / 怎么验证没改坏）。
7. [机检] 行数预算见「文档类型总表」；超限部分逐段自问「删掉后人类理解或执行者出错率会上升吗」，不会则删。
8. [机检] 版本区知识文档（design/testing-guide/roadmap）frontmatter 四字段齐（title/owner/status/last_reviewed）、status 在封闭词表；AGENTS.md、_index.md 豁免。
9. [机检] 每个治理域根 AGENTS.md 存在且 Project Map 登记完整；模块 AGENTS.md 的建/缺都能对应三信号。
10. [机检] 引用真实性：AGENTS.md 与版本区文档中命令、路径、链接、文档名逐一核对存在（文档引用不存在的命令比没有文档更糟）。
11. [机检] 过程件隔离：changelog/handoff/pending/工作稿全在已登记、被 .gitignore 排除的临时目录（git check-ignore 通过）；版本区检索不到中间文件。
12. [机检] 引用形式合规：无本机绝对路径、跨仓库无文件系统相对路径、跨仓库引用带显式 ref、未链接被 .gitignore 排除的内容、引用中不出现行号、相对链接/图片目标真实存在（无死链）。机检对行号会匹配反引号段、链接目标与正文里的「文件.ext:行号」形态，并剥掉 URL 避免 http://host:port 误报；链接存在性只验相对链接/图片，跳过行内代码里的示例语法。
13. [评] 渐进式披露成立：同一主题越靠根部展开越浅（入口只有「一行/一句 + 指针」），根部无可直接下沉的细节，无层序倒挂。
14. [评] 每份最终文档都被上层入口指到（无孤儿；指针存在性由第 10 条兜底）。
15. [机检] roadmap 合规：每域一份 ≤60 行、每条有验收判据、已实现项已删除、无进度/工时/任务分解、已在根 AGENTS.md 版本区表登记。

# 反模式（红线已覆盖的不重复）

- 把设计文档写成需求文档或宣传文档。
- 为让 Agent 好检索而牺牲人读性：解释删成关键词、依据换指针、文档写成纯索引。
- 复制其他文档/代码内容「方便读者」。
- 写「本模块很重要/性能优越」这类无据形容词。
- 状态机无「禁止直接改状态」的唯一入口声明。
- 红线或「坑」无来源（事故/压测/评审），或可被随意绕过且无检查兜底。
- 同一概念在体系内用两个名字（如 Project Map / 模块地图并存）。
- roadmap 写成 wishlist：条目无验收判据，或混入进度/工时/任务分解、实现后不删（使它退化成任务清单）。

# 机检与评审设施（本技能自带，与本 SKILL.md 同目录）

- scripts/check-docs.mjs（零依赖，Node ≥ 22）：node <技能目录>/scripts/check-docs.mjs <治理域根>。退出码 0 全过 / 1 有 ERROR / 2 根目录不可读。机检以下 [机检] 项的机械部分：行数预算（第 7）、frontmatter 与 status（第 8）、引用真实性：相对链接/图片目标是否存在（死链即 ERROR，第 10、12 的机械部分）、过程件隔离（第 11）、引用形式：绝对路径/跨仓库相对路径/行号（第 12）、roadmap 行数与登记（第 15 的机械部分）、孤儿文档（第 14 的启发式）。它不判语义（第 1–6、13 条留 [评]）。可拷进项目或接入 CI。
- review-prompt.md：派「对抗评审子智能体」用的提示词模板，覆盖全部 [评] 项；把待审文档根路径填进去即可用。
