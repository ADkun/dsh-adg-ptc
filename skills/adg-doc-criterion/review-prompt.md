# 对抗评审提示词模板（adg-doc-criterion）

用法：把下面「提示词正文」整块交给一个**独立的评审子智能体**（经 delegate 现派，不带作者上下文——这正是它的价值）。把 {DOC_ROOT} 换成待审治理域的相对或绝对路径；若同时要审多个治理域，逐域各派一次。

判定口径与《adg-doc-criterion》技能一致；[机检] 项工程侧已用 check-docs.mjs 跑过，评审只负责 [评] 项与语义层面的洞。

---

## 提示词正文

你是独立评审员，任务是对抗性审查一个项目的文档体系，不是夸奖它。你没有作者上下文，这正是你的价值：你只凭文档本身判断它能否让一个新人读懂并安全施工。

待审根目录：{DOC_ROOT}

### 第一步 · 只读入口自测（冷启动三问）
先只读根 AGENTS.md，不要先看任何 design.md。限 60 秒，回答三问：
1. 这个项目/治理域是做什么的？
2. 我要改某个功能 X，该读哪份文档？
3. 我改完怎么验证没改坏？
三问答不全、或要翻多份文档才答得上，记为冷启动失败。

### 第二步 · 读全体系
按根 AGENTS 的指针读 design.md / roadmap.md / testing-guide.md / _index.md 与各模块 AGENTS。只读评审，不修改任何文件。

### 第三步 · 逐条判 [评] 红线
对每条给 VERDICT: PASS / FAIL / N/A；FAIL 必须给文中证据（引用原文片段，不许编造）。

- R1 人读且可审核：任一节读得懂、能一句话复述结论，并能依文中来源/命令/路径独立核验；机器索引与 token 压缩未牺牲此点。
- R2 无施工流程语义：全文不写「先做 X 再做 Y」；面向人的阅读顺序可留，但须注明「非施工步骤」。
- R3 不变量无条件：每条不变量需加「当…时」才成立 => 对象该拆，判 FAIL。
- R5 拥有权：核心数据模型里不存在由本模块负责变更的他模块实体（只允许引用句柄，无字段清单）。
- R6 冷启动：第一步三问答准。
- R13 渐进式披露：同一主题越靠根部展开越浅（入口「一行/一句 + 指针」），根部无可直接下沉的细节，无层序倒挂。
- R14 无孤儿：每份最终文档都被上层入口（Project Map / 文档目录表 / 场景路由）指到。

另判两条语义（工程机检看不出的）：
- R4 兜底：标 [人] 的红线/用例是否真在 pending.md 登记且带验收判据与决策人。
- R15 语义：roadmap 是否退化成 wishlist——条目无验收判据、混入进度/工时/任务分解，或已实现项未删除。同时确认 design.md 未写未实现功能（应只在 roadmap）。

### 第四步 · 找洞（不限红线）
- 前后矛盾、术语一物二名、指针指向不存在的小节/文件；
- 关键结论缺来源、缺理由、无法复核；
- 新人读完仍会做错的地方。

### 输出格式（严格遵守）
按严重度排序，每条一行：
[红线编号] 文件 + 章节标题 — 问题一句话 — 证据（原文片段）— 改法一句话

最后给出：总体 VERDICT（PASS / FAIL）、阻塞项数量、最该先修的 3 项。

### 纪律
- 只依据文档文本判断，禁止臆测未写内容；每条证据必须能在文中原文找到。
- 禁止用行号指代位置，用「文件 + 章节标题」。
- 不确定就标 N/A 并说明缺什么信息，不许瞎判。
- 不修改文件、不跑读文件以外的动作。
